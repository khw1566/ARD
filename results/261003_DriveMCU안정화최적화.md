# DriveMCU 안정화 및 최적화 보고서
## 1. 분석 범위와 판단
DriveMCU Arduino/PlatformIO 펌웨어를 분석하고 수정했다. 사용자가 언급한 특정 환경의 시리얼 로그와 재현 조건은 아직 제공되지 않았으므로, 아래 내용은 실제 증상의 확정 원인이 아니라 코드에서 확인한 결함 및 수정 결과다. SDK 또는 보드 플랫폼을 새로 설치하거나 교체하지 않았다.

## 2. 확인한 문제와 수정
### 센서 누락 또는 고장 시 지연과 초기화 실패 후 접근
기존 코드는 AHT20, BMP280, OLED 초기화에 실패해도 이후 읽기와 표시를 실행했다. 특히 OLED 버퍼 할당 실패 후 표시 호출은 잘못된 메모리 접근 위험이 있었다. 설치된 Adafruit AHTX0 2.0.6의 begin/getEvent에는 BUSY를 제한 없이 기다리는 루프가 있었다.
- 초기화 성공 여부를 보관하고 실패한 주변 장치를 건너뛴다.
- AHT20 초기화와 측정을 BoundedAht20 모듈로 분리했다. 초기화 BUSY 대기는 단계별 200ms, 측정은 상태 기반으로 진행하고 250ms를 넘으면 실패 처리한다. 장기적으로 갱신되지 않은 AHT20 값은 유효하지 않은 것으로 표시한다.
- I²C 거래 타임아웃을 20ms로 설정했다. OLED와 환경 센서, 선택적 ToF 및 버스 속도 변경은 loop에서 처리하고, 하트비트는 동기화된 환경 값 복사본을 읽는다.
- OLED 시간 조회의 기본 5초 대기를 제거하여 NTP가 없는 환경에서도 getLocalTime(..., 0)으로 즉시 반환한다.

### ToF 없는 개루프 운용
사용자의 앞선 요구에 따라 ARD_ENABLE_TOF 기본값을 0으로 설정했다. ToF 초기화 및 주기 읽기를 하지 않으며 mzm1 PID 활성화 요청은 거절한다. 수동 Z 메뉴도 진입 위치를 기준으로 ±15mm 범위를 Steps/mm로 변환하는 개루프 방식으로 바꿨다.
- PC home은 X/Y 논리 원점 복귀이며 Z의 ToF 목표를 숨겨서 변경하지 않는다.
- 기존 mza 자동 보정은 네트워크 작업을 2.5초 막고 이동 완료를 확인하지 않아 제거했다. 현재 mza는 오류를 반환하며 mzs<Steps/mm>로 실측 보정값을 설정한다.
- 실제 레일 중앙 정렬과 탈조 여부는 개루프 스텝 카운터만으로 확인할 수 없다.

### 통신 지연과 명령 처리
기존 TCP는 readStringUntil로 불완전한 줄을 기다렸고, 세션 유지 동안 시리얼과 GPS 처리가 지연됐다. 입력 버퍼는 길이 제한 없이 성장했고 명령 큐가 가득 차도 ACK:OK를 반환했다.
- BoundedLine으로 TCP와 시리얼을 처리한다. 최대 명령 길이는 127 ASCII 문자이며, 과도한 길이나 바이너리 문자가 포함된 줄 전체를 버린다. 일부만 잘린 모터 명령을 실행하지 않는다.
- 줄바꿈이 완료된 명령만 실행한다. TCP 바이트 대기 500ms, 연결 총 1초 제한을 적용하고 명령 응답 후 연결을 닫는다.
- 각 통신 루프의 UART 처리량을 제한하고 TCP 수신은 대기 루프 없이 처리한다.
- CommandValidation으로 정수 형식, 누락된 값, 범위, NaN/Inf, 잘못된 축과 명령을 검증한다. 정수 명령의 지수 표기도 거절하여 검증값과 String.toInt 실행값이 달라지는 것을 막았다.
- 큐 포화와 거절된 명령은 ERR:REJECTED로 응답한다. status 프로토콜 1의 기존 필드는 유지하여 선별 파이프라인과 호환된다.
- HTTP 연결 타임아웃을 명시했다. GPS 시간 동기화 요청은 통신 명령 처리 경로에서 하트비트 작업으로 옮겼다.
- Wi-Fi 연결 실패 시 설정 메뉴에 자동으로 갇히지 않고 오프라인 운용을 이어간다. 10초 간격 재연결 요청 및 연결 복구 시 TCP 서버 재시작을 추가했다. 설정 메뉴는 명시적 w 명령으로 들어간다.

### 모터 정지와 동시성
기존 코드는 정지 시 큐를 비워도, 모터 작업이 이미 꺼내어 지연 대기 중인 명령은 남아 있었다. 이후 새 명령이 stopActive를 해제하면 이전 명령이 실행될 수 있었다. PID 데드존에서는 이미 보유한 비재귀 mutex를 다시 획득하려 하여 정지가 실행되지 않았다.
- emergencyStop으로 정지 처리를 통합하고 큐, 대기 상태, PID, 현재 목표와 드라이버 활성 상태를 함께 정리한다. 명령 세대 번호로 이전에 꺼낸 작업도 무효화한다.
- 같은 motorMutex 안에서 처리하는 PID 정지의 중복 mutex 획득을 제거했다.
- 정지 플래그, PID 모드 및 수동 모드는 atomic으로 공유한다. 수동 목표와 드라이버 활성화도 모터 mutex 안에서 정지 상태를 재확인한다.
- 수동 메뉴 진입 시 기존 원격 이동을 정리하고, 수동 운용 중 새 원격 구동 명령을 거절한다. 정지는 허용한다.
- 전역 disable은 펄스를 계속 계산하며 드라이버만 끄던 방식에서 실제 명령 정리 및 정지로 변경했다.
- 버튼 이벤트 전달의 읽기/초기화를 임계 구역으로 묶어 입력 유실 가능성을 줄였다.

### 메모리와 진단
- 로그 큐는 strdup/free 포인터 소유 방식 대신 160바이트 고정 메시지로 변경했다. 과도한 로그는 카운트 후 버리며 모터 작업을 기다리게 하지 않는다. String과 HTTPClient 자체의 동적 할당까지 제거한 것은 아니다.
- RTOS 큐, mutex 및 작업 생성 실패를 확인한다. 실패 시 모터를 비활성화하거나 정지시키고 FATAL을 출력한다.
- 부팅 시 리셋 원인, 힙 및 ToF 모드를 출력한다. 주기적인 Health에는 현재/최소 힙, 버려진 로그 수 및 하트비트 작업 스택 여유를 기록한다.
- Arduino 3의 LEDC API에 맞춰 부저 호출의 인수를 채널 0에서 GPIO 4로 수정했다.

## 3. 파일과 검증
- DriveMCU/src/main.cpp: 주변 장치 및 통신 작업 경계, 모터 정지, 오류 응답, 진단.
- DriveMCU/include/BoundedLine.h: 길이 제한 및 전체 줄 검증.
- DriveMCU/include/BoundedAht20.h: 제한 시간과 상태 기반 환경 센서 접근.
- DriveMCU/include/CommandValidation.h: 모터 및 설정 명령 검증.
- DriveMCU/test/native/: 실제 헤더와 실제 motorTask/emergencyStop 함수를 사용한 MSVC 테스트. run_tests.py가 펌웨어에서 함수를 추출하여 가짜 RTOS/모터와 컴파일한다.
네이티브 테스트는 긴 입력, 분할 입력, 바이너리 입력, 잘못된 수치, 센서 미연결, BUSY 고착, 오래된 센서 값, millis 오버플로, 지연 명령 정지 후 재개, 오래된 큐 항목, PID mutex 및 정지 처리를 검사한다.
PC 선별 회귀 테스트 20개도 통과했다. PlatformIO 최종 빌드가 성공했다. 정적 RAM은 67,736 / 327,680바이트(20.7%), 프로그램 플래시는 1,879,227 / 3,145,728바이트(59.7%)다. Arduino 3.3.11 환경을 유지했으며 기존 BluetoothSerial 향후 지원 중단 경고만 남았다. 실제 Wi-Fi 장애, 전원 환경, 모터 부하, 펄스 파형 및 장시간 운용은 실물 시험이 필요하다.

## 4. 적용 및 현장 확인
수정된 DriveMCU 펌웨어를 업로드한다. 프로젝트 루트에서 `pio run -d ARD_software/DriveMCU -t upload`를 사용한다. 생성된 앱 바이너리는 `DriveMCU/.pio/build/esp32-wroom32d/firmware.bin`이다. 이번 작업에서는 보드 업로드를 수행하지 않았다. 부팅 로그에 ToF=disabled (open loop)가 표시되어야 한다. PC 선별에는 이전에 추가한 status 프로토콜을 계속 제공한다.
권장 실물 확인은 주변 센서를 연결하지 않은 부팅, 서버/NTP 접근이 없는 운용, Wi-Fi 끊김과 복구, 지연 명령 중 x 정지 후 새 이동, 연속 분류다. 불안정 현상이 남으면 부팅 직전 로그와 [Boot]/[Health] 출력을 기준으로 다음 원인을 좁힌다.
AccelStepper의 작업 기반 펄스 생성은 유지했다. vTaskDelay(1) 및 다른 작업의 스케줄링 영향을 받으므로 고속 모터의 펄스 간격을 하드웨어 타이머 수준으로 보장하는 변경은 아니다. 처리량 또는 지터 개선 수치를 실측했다고 주장하지 않는다.

참고: 명시적으로 진입하는 Wi-Fi/Bluetooth 설정 메뉴는 사용자 입력 대기 방식으로 유지했다. 일반 TCP 수신 경로와는 별도이며, w 진입 전에 모터를 정지한다.
