# JC1060P470C 펌웨어 문제 원인 및 조치 보고서

작성일: 2026-10-24 (한국 시간)

대상: `ARD_ESP-IDF/JC1060P470C`

최종 상태: 사용자 정상 동작 확인 — “지금 잘되고 있어”

## 1. 핵심 결론

이번 문제는 화면 출력 설정, 초기화 이식, 화면 갱신 경로, 빌드 의존성의 여러 항목을 순차적으로 확인한 사례다.
빌드·업로드 성공만으로 실제 LCD 패널에 맞는 설정과 표시 품질까지 검증되지는 않았다.

| 구분 | 확인한 내용 | 조치 | 원인 판단 수준 |
|---|---|---|---|
| 초기 흰 화면·회색 줄무늬 | 실제 부팅 로그가 `JD9165 V1 panel up, 54 MHz`였음 | 실제 `sdkconfig`를 V2로 변경 | V1 설정 적용은 로그로 확정. V2 변경 후 화면 표시 성공은 사용자 확인 |
| 초기화 명령 누락 | ESPHome에서 제조사 표 뒤에 추가하는 RGB565·색 반전 해제 명령이 이식본에는 없었음 | `COLMOD=0x55`, `INVOFF` 추가 | 소스상의 누락은 확인. 이것만으로 안개 현상이 해결되지는 않았음 |
| 안개처럼 밝은 화면·CAM 버튼 잔상 | 사용자가 검은 영역에 이전 버튼 모양이 남는다고 보고 | 전체 화면 동기 복사, 불투명 배경, 출력 오류 확인, 흰색→검은색 진단 추가 | 여러 조치를 함께 적용했으므로 단일 원인은 미분리. DMA2D 하드웨어 결함으로 확정하지 않음 |
| 후속 빌드 실패 | `fatal error: esp_cache.h: No such file or directory` | 메인 컴포넌트에 `PRIV_REQUIRES esp_mm` 등록 | 헤더 소유 컴포넌트의 직접 의존성 누락으로 확정 |

최종 수정 후 사용자가 정상 동작을 확인했다. 다만 기능별 시험 결과와 최종 성공 빌드 전체 로그는 별도로 수집하지 않았다.

## 2. 대상 환경

| 항목 | 확인값 | 근거 |
|---|---|---|
| 보드 | GUITION JC1060P470C | 프로젝트 및 사용자 설명 |
| MCU | ESP32-P4, chip revision v1.3 | 사용자 부팅 로그 |
| SDK | ESP-IDF v5.5.5 | 부팅·컴파일 로그 및 로컬 SDK |
| LCD | JD9165, 1024×600, MIPI-DSI | 프로젝트 설정 |
| LCD 컴포넌트 | `esp_lcd_jd9165` 2.0.2 | 부팅 로그 및 설치 소스 |
| UI | LVGL 9.2.2, RGB565 | 의존성 및 설치 소스 |
| 터치 | GT911, I2C 주소 0x5D에서 인식 | 사용자 부팅 로그 |

PSRAM 부팅 검사 통과는 기본 메모리 검사 결과다. 프레임버퍼 복사, 캐시 동기화, 화면 갱신의 모든 경로가 정상이라는 뜻은 아니다.

## 3. 최초 화면 문제: 실제 패널 설정과 적용 설정의 불일치

### 증상과 근거

사용자는 빌드와 업로드는 성공했으나 화면이 흰색·회색 줄무늬로 나오고, 스와이프에 줄무늬가 반응한다고 보고했다.
첫 부팅 로그에는 다음 내용이 있었다.

```text
JD9165 V1 panel up, 54 MHz
GT911 at 0x5D
```

터치 입력은 I2C의 GT911 경로이고, LCD 영상은 MIPI-DSI 경로다. 따라서 터치 반응이 있다는 사실만으로 LCD 패널 초기화와 출력 타이밍이 맞다고 판단할 수 없었다.

V2 설정 변경을 안내한 뒤 받은 새 로그에서도 패널은 여전히 V1이었다. 이때 앱 컴파일 시각은 `Oct 24 2026 15:59:13`으로 바뀌어 있었다.
즉, 새 앱을 빌드했지만 실제 패널 선택은 계속 V1인 상태가 확인됐다.

### 수정

실제로 사용되는 `sdkconfig`를 다음과 같이 변경했다.

```text
# CONFIG_ARD_PANEL_V1 is not set
CONFIG_ARD_PANEL_V2=y
```

| 설정 | 픽셀 클럭 | 수평 동기/후면/전면 구간 | 수직 동기/후면/전면 구간 |
|---|---:|---|---|
| V1 | 54 MHz | 40 / 160 / 160 | 10 / 23 / 12 |
| V2 | 52 MHz | 24 / 136 / 160 | 2 / 21 / 12 |

타이밍뿐 아니라 패널 리비전에 맞는 제조사 초기화 표도 함께 선택하도록 했다.
또한 `build.ps1`에서 실제 `sdkconfig`의 선택값을 출력하도록 보완했다.

```text
JC1060P470C panel selected in sdkconfig: V2
```

이 변경 후 사용자는 화면 표시가 성공했다고 보고했다. 이후에도 안개처럼 밝은 현상이 남았으므로 추가 조사를 진행했다.

## 4. 초기화 이식에서 빠진 후처리 명령

기존 이식본은 ESPHome의 제조사 초기화 표를 가져왔지만, ESPHome 공통 처리에서 표 뒤에 추가하는 명령까지 모두 반영하지는 않았다.

설치된 JD9165 2.0.2 소스도 `dev.bits_per_pixel=16` 설정만으로 `COLMOD` 명령을 전송하지 않는 것을 확인했다.
따라서 호스트 측 RGB565 설정과 별도로 패널 측 픽셀 형식도 명시하도록 보완했다.

```c
C(LCD_CMD_COLMOD, 0x55), // RGB565
{LCD_CMD_INVOFF, NULL, 0, 0},
```

두 명령은 페이지 0으로 돌아온 뒤, sleep-out 대기 후 display-on 전에 배치했다.
V1·V2 표 양쪽에 적용했다.

**이 누락은 소스 비교로 확인했지만, 안개·잔상의 단독 원인으로 확정하지 않았다.**
사용자가 이 조치 후에도 안개 현상과 잔상을 보고했기 때문이다.

비교 근거: [ESPHome 패널 정의](https://github.com/esphome/esphome/blob/dev/esphome/components/mipi_dsi/models/guition.py),
[ESPHome 공통 초기화 후처리](https://github.com/esphome/esphome/blob/dev/esphome/components/mipi/__init__.py).

## 5. 안개 현상과 검은 영역의 이전 화면 잔상

### 확인한 증상

- 가운데가 안개처럼 밝지만 글자와 버튼 위치는 정상이라는 사용자 설명이 있었다.
- 제공된 사진에서는 세로·가로 색상 막대의 배열과 경계를 확인할 수 있었다.
- 사용자는 검은 화면에 이전 화면이 지워지지 않고, 오프라인 CAM 영역에도 다른 버튼 잔상이 보인다고 보고했다.

색상 막대 사진은 기본적인 패턴 출력을 확인하는 자료다. 사진만으로 감마·휘도·잔상 원인을 정량 판정하지는 않았다.

### 기존 경로에서 확인한 사항

기존 경로는 100줄짜리 LVGL 부분 버퍼 두 개를 사용하고, DMA2D 비동기 복사 완료 콜백에서 버퍼 사용 완료를 알리는 구조였다.
또한 `esp_lcd_panel_draw_bitmap()` 반환값을 확인하지 않았다.

LVGL 기본 탭 페이지 스타일은 투명하며, 기존 화면은 상위 배경과 테마의 덮어그리기에 의존하는 부분이 있었다.
이 사실만으로 배경 투명도가 잔상의 원인이라고 확정할 수는 없지만, 진단 과정에서 배경 덮어그리기를 명시적으로 만들었다.

### 수정한 경로

1. 진단용 `ARD_LCD_SYNC_FULL_REFRESH` 모드를 추가하고 현재 로컬 설정에서 활성화했다.
2. 전체 화면을 다시 렌더링하고, DMA2D 대신 동기 CPU 복사로 출력하도록 했다.
3. 동기 복사가 반환된 뒤 LVGL에 버퍼 사용 완료를 알리도록 했다.
4. 출력 오류를 기록하고, 실패 시에도 LVGL이 완료 신호를 무기한 기다리지 않도록 했다.
5. 화면·탭 페이지·카메라 패널 배경을 명시적으로 불투명하게 설정했다.

이 조치는 부분 갱신 범위, 비동기 복사, 배경 덮어그리기의 영향을 함께 분리하기 위한 안정화·진단 조치다.
각 변경을 하나씩 되돌려 비교한 결과는 없으므로, “DMA2D 자체 고장” 또는 “배경 투명도만의 문제”로 결론내리지 않는다.

### 추가한 출력 진단

부팅 시 다음 순서로 표시하도록 했다.

```text
세로 하드웨어 색상 막대 4초
→ 가로 하드웨어 색상 막대 4초
→ 실제 프레임버퍼 흰색 3초
→ 실제 프레임버퍼 검은색 3초
→ 일반 UI
```

색상 막대는 DSI 호스트가 직접 생성한다. 흰색·검은색 단계는 실제 출력 프레임버퍼를 덮어쓰고 캐시를 동기화한다.
검은색 단계에는 0이 아닌 픽셀 수를 읽어 다음과 같은 진단 로그를 남기도록 했다.

```text
LCD test: black framebuffer nonzero pixels=0
```

위 문장은 **추가한 진단 로그의 형식**이다. 사용자가 이 값이 0인 최종 로그를 제출한 것은 아니다.
0으로 확인된 프레임버퍼에서도 모양이 남는다면 UI 데이터 잔류와 구분하여 출력·패널 구동 경로를 조사할 수 있다.

## 6. 후속 빌드 실패: esp_mm 의존성 누락

### 실제 오류

사용자가 제출한 Ninja 로그의 첫 실제 오류는 다음과 같다.

```text
FAILED: esp-idf/main/CMakeFiles/__idf_main.dir/bsp_display.cpp.obj
fatal error: esp_cache.h: No such file or directory
```

`esp_cache.h` 파일은 설치된 SDK의 `components/esp_mm/include/`에 존재했다.
그러나 캐시 동기화 진단 코드를 추가하면서, 이를 직접 사용하는 메인 컴포넌트의 `esp_mm` 의존성 등록을 누락했다.
그 결과 컴파일러의 헤더 검색 경로에 해당 컴포넌트의 include 경로가 들어오지 않았다.

### 수정

메인 `CMakeLists.txt`의 `idf_component_register()`에 다음을 추가했다.

```cmake
PRIV_REQUIRES esp_mm
```

재구성·재빌드를 안내했고, 이후 사용자가 현재 정상 동작한다고 확인했다.
이 빌드 오류는 후속 진단 코드의 의존성 누락이며, 최초 V1 설정으로 인한 화면 문제와는 발생 단계가 다르다.

## 7. 함께 추가한 설정 기능

사용자 요청에 따라 메인 **Settings** 화면을 만들고 다음 분류를 추가했다.

| 분류 | 구현 내용 |
|---|---|
| Display | 밝기 5~100%, 빠른 선택 버튼, 변경 즉시 적용, 조작 종료 후 저장, 부팅 시 복원 |
| Network | Wi-Fi 검색·목록 선택, SSID 직접 입력, 비밀번호 화면 키보드, 숨김·표시, 연결 상태·IP 표시 |
| 저장·복구 | IP 수신 후 Wi-Fi 정보 저장, 실패 시 이전 설정 복구 시도 |
| 작업 분리 | 검색·연결·저장을 별도 작업 태스크에서 처리, UI의 RSSI 조회도 캐시값 사용 |

이 기능 추가 자체를 최초 디스플레이 장애의 원인으로 보지는 않는다.
최종 정상 동작 확인은 사용자 보고이며, 밝기 저장 후 재부팅 복원·오입력 복구 등 각 항목의 개별 시험 결과는 별도로 기록되지 않았다.

## 8. 현재 설정과 재발 방지 사항

현재 로컬 설정 확인값은 다음과 같다.

```text
CONFIG_ARD_PANEL_V2=y
CONFIG_ARD_LCD_BOOT_TEST=y
CONFIG_ARD_LCD_SYNC_FULL_REFRESH=y
```

| 항목 | 유지·확인할 내용 |
|---|---|
| 패널 선택 | 빌드 시 실제 `sdkconfig` 선택값과 부팅 시 V2/52 MHz 로그를 확인한다. |
| 새 설정 생성 | 최초 보고서 작성 당시 기본 선택은 V1이었다. 같은 날 GitHub 병합·배포 정리에서 `sdkconfig.defaults`와 Kconfig에 V2 + 전체 화면 동기 갱신 기본값을 반영했다. 구형 V1 패널은 별도로 V1을 선택한다. |
| 초기화 이식 | 제조사 표뿐 아니라 원본 프레임워크의 픽셀 형식·반전·sleep-out·display-on 후처리도 함께 확인한다. |
| SDK API 추가 | 헤더 존재·함수 선언 확인에 더해, 헤더를 제공하는 컴포넌트의 직접 의존성 등록도 확인한다. |
| 화면 갱신 | 진단 모드를 정상 경로로 유지할지, 비교 시험 후 부분 갱신으로 복귀할지 결정한다. 현재 성공 상태를 기준으로 기록한다. |

전체 갱신 모드의 LVGL 그리기 버퍼는 기존 409,600 bytes에서 1,228,800 bytes로 늘었다.
별도 출력 프레임버퍼는 1,228,800 bytes로 동일하다. CPU·PSRAM 사용량이 증가하며, 화면 찢어짐 방지나 최대 성능이 검증된 상태는 아니다.
부팅 출력 진단이 켜져 있어 일반 UI 시작까지 약 14초의 의도적인 대기가 있다.

## 9. 별도로 남은 확인 항목

초기 로그에는 다음 경고·오류도 있었다.

```text
Version mismatch: Host [2.12.0] > Co-proc [2.3.0]
Gamepad (BLE) unavailable: ESP_ERR_NOT_SUPPORTED
```

이는 C6 보조 펌웨어와 BLE 경로의 별도 확인 항목이다. 이후 해당 경고가 사라진 로그는 제출되지 않았으므로 해결 여부는 미확인으로 남긴다.
이번 화면 장애와 직접적인 인과관계도 확정하지 않았다.
