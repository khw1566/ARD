# ImageSender 응답·촬영 실패 복구·수동 초기화

## 사용자 증상과 소스에서 확인한 경로

PC에서 첫 선별은 성공했지만 JC1060에서 두 번째 선별을 시작했을 때 이미지 수신 타임아웃이 발생했다. 이후 재시도가 막혔다. 실물 로그나 패킷 캡처를 수집한 것은 아니므로 무선·센서·서버 중 최초 지연 원인을 확정하지는 않았다. 다음 소스 결함을 수정했다.

- ImageSender TCP 서버가 촬영 작업의 수락 여부와 무관하게 ACK를 보냈다. 촬영 중 요청도 알림 카운터로 합쳐져 뒤늦은 추가 촬영이 될 수 있었다.
- 촬영 태스크가 진단 로그의 HTTP 전송을 기다렸다. HTTP 로그·폴링·업로드가 공유 응답 버퍼와 무기한 대기 mutex를 사용했다.
- 프레임이 새것인지 확인하지 않고 첫 프레임을 무조건 버리고, NULL 프레임에도 추가 4초 대기를 반복했다.
- PC는 촬영 요청과 받은 이미지의 대응 ID를 검사하지 않았다. inbox 잠금을 잡은 채 촬영 명령을 전송했다.
- PID로 촬영 위치에 이동한 뒤 카메라만 실패해도 선별기가 `x` 비상정지를 걸었다. 정지 래치가 다음 PID 시작을 막을 수 있었다.
- PC 시작 요청이 HTTP 409로 거절됐을 때 버튼 비활성 상태가 남았다. 기존 초기화 버튼은 트레이 `home`만 전송했고, JC1060의 STOP은 오류 뒤 비활성화됐다.

## 1. ImageSenderMCU 펌웨어

- TCP 5003의 `capture <id>`는 실제 작업 슬롯을 확보한 뒤 `ACK:CAPTURE_START,<id>`를 보낸다. 바쁘면 `ERR:BUSY`다. 마지막 수락 ID의 중복 요청은 ACK만 재전송한다. ID 캐시는 RAM이며 부팅을 넘는 영속 보장은 아니다.
- 줄 끝까지 받은 명령만 실행하고 수신 대기를 제한했다. 기존 `c`, `capture`, `ping`도 유지한다.
- `reset`/`reset_camera`는 카메라 소유 태스크에 재초기화를 예약한다. `ACK:RESET_PENDING`은 완료가 아니다. `ping`의 `busy`, `reset`, `ready`, `id`, `resets`, 성공/실패 카운터로 상태를 확인한다.
- 재초기화 중 이전 작업의 프레임은 세대 번호로 송신을 막는다. 반환된 프레임을 소유 태스크에서 정리한 뒤 드라이버를 재초기화한다.
- 카메라 프레임의 시작 시각을 설치된 esp32-camera 드라이버와 같은 `esp_timer_get_time()` 기준으로 비교한다. 이미 새 프레임이면 버리지 않고, NULL이면 드라이버의 4초 대기 뒤 즉시 실패를 반환한다. 프레임 실패 시 드라이버 재초기화 후 1회 다시 획득한다.
- 진단 로그는 1칸 큐로 넘겨 촬영 태스크가 네트워크 로그를 기다리지 않게 했다. 새 로그가 이전 미전송 로그를 대체할 수 있다. HTTP 응답 버퍼는 요청별로 분리했다.
- 폴링/하트비트 timeout은 각 1초, 진단 로그 0.5초, HTTP 업로드 5초로 제한했다. Wi-Fi 절전은 기존 소스에서도 이미 꺼져 있어 변경하지 않았다.
- 수락된 촬영/리셋이 30초 넘게 멈추면 MCU를 재시작하는 감시 태스크를 추가했다. 유휴 상태에는 이 감시가 재부팅을 반복하지 않는다. Wi-Fi/NVS 설정은 지우지 않는다.
- UART `r`로도 카메라 재초기화를 요청한다.

태스크/메모리: 감시 태스크 스택 2048바이트와 로그 큐 200바이트를 추가했다(TCB/큐 관리 메모리 별도). HTTP 동시 요청의 실제 힙 사용량과 장시간 안정성은 측정하지 않았다.

## 2. PC 촬영·재시도·수동 초기화

- `core/camera_control.py`가 선별 촬영마다 ID를 만든다. ACK가 유실되면 같은 ID로 다시 요청한다. 새 프로토콜을 시도한 뒤 결과가 모호하면 ID를 유지한 채 폴링으로 넘긴다. 명시적으로 구 펌웨어임을 확인한 경우 기존 단순 촬영 방식으로 호환한다.
- **ID가 있는 선별 단일 촬영은 HTTP `/upload`로 전송**하고 `X-ARD-Capture-ID` 헤더를 보낸다. 일반 촬영/미리보기의 기존 UDP/TCP 설정은 유지한다. 구 펌웨어의 ID 없는 촬영에는 엄격한 요청별 프레임 대응을 보장할 수 없다.
- FrameInbox는 명령 전송 동안 잠금을 유지하지 않는다. 요청 ID가 일치하는 새 프레임만 선별에 사용한다. 최근 태그 프레임은 최대 4개 보관하여 뒤따른 미리보기가 해당 프레임을 덮어쓰지 못하게 한다. 과거 태그 촬영은 별도 AI 분석을 다시 유발하지 않는다.
- 촬영 대기는 명령 시간까지 포함해 25초로 제한한다. 첫 실패에는 카메라 리셋 완료를 확인한 뒤 1회 재촬영한다. 최종 촬영 실패에는 다시 카메라 상태를 초기화하고 재시도 가능 여부를 보고한다.
- 트레이 X/Y를 움직이기 전의 **촬영 단계 실패**에는 PID를 끄고, 불필요한 비상정지 래치를 새로 만들지 않는다. 실제 모터 이동/위치 검증 오류와 사용자 중단은 기존 비상정지를 유지한다. 임의로 정지 래치를 해제하거나 현재 위치를 원점으로 바꾸지 않는다.
- `/api/sorting/reset`을 추가했다. 작업이 끝난 뒤 수동 초기화를 요청하면 다른 제어를 예약으로 막고, 먼저 모터 큐를 정지시킨 뒤 촬영 상태 비우기 → 카메라 재초기화 완료 확인 → 트레이 X/Y `home` → 실제 정지·X/Y=0 확인을 수행한다. 레일 Z의 원점과 추정 스텝은 유지한다. 다음 선별 시작 때 기존 설정대로 120mm 촬영 위치에 정렬한다.
- 진행 중인 작업은 먼저 중단해야 초기화할 수 있다. 오래된 작업을 실행 중인 채 강제로 잠금을 풀지 않는다. 초기화 실패를 준비 완료로 표시하지 않는다.
- PC 버튼은 실행 중 `선별 중단`, 그 외에는 `초기화 / 재시도 준비`다. 409로 시작이 거절돼도 버튼이 영구 비활성화되지 않는다. 초기화가 필요한 오류는 시작을 막고 초기화 버튼은 사용할 수 있게 한다.
- JC1060 메인 화면에도 비실행 시 `초기화`, 실행 중 `STOP`을 제공한다. 같은 PC API를 사용한다.

## 3. 배출함 가이드

PC 사이드바의 전방 가이드를 금속=좌측 전방, 종이=우측 전방으로 수정했다. ToF 목표는 70mm로 표시하고 후방은 120mm로 갱신했다. **분류별 실제 모터 명령, 90/270도 각도, 분류 알고리즘은 변경하지 않았다.** 사용자 관찰에 따른 UI 좌우 표기 수정이다.

## 실행한 검사

- Python 158개 통과: 카메라 명령/프레임 대응/타임아웃 후 재시작/수동 초기화/기존 선별·레일·조그·보드 설정 등. 모두 가상 보드 또는 모의 HTTP 응답이며 실물 검증이 아니다.
- 새 회귀 사례: ACK 유실 시 동일 ID 재전송, BUSY 시 중복 폴링 금지, 이전 프레임/미리보기 배제, 촬영 타임아웃 후 다음 실행 성공, 리셋 예약 중 새 시작 차단, X/Y 복귀가 Z 추정값을 지우지 않음.
- Node 선별 대시보드 및 PID UI 검사 통과. 409 뒤 버튼 복구와 초기화 API 호출을 확인했다.
- Python AST, C/C++ 문자열·괄호, 변경 파일 `git diff --check` 통과. SDK의 HTTP `user_data`, 카메라 타임스탬프와 deinit 선언을 설치 소스에서 확인했다.
- 한글 폰트 C 소스를 다시 생성했다. 이 생성은 컴파일이 아니다.
- 기존 C 카메라 테스트 fixture도 새 타임스탬프/리셋 API에 맞췄지만 **빌드가 금지되어 실행하지 않았다.** CMake 진단 테스트도 실행하지 않았다.
- 펌웨어 빌드·링크·플래시, 실제 JC1060 화면/터치, 무선 응답 시간, 실물 연속 선별은 검증하지 않았다.

## 사용자 적용

PC 프로그램을 재시작하고 ImageSenderMCU와 JC1060 소스를 사용자가 빌드·업로드해야 한다. 이번 변경은 아직 장치에 적용되지 않았다.

```powershell
& "C:\Users\work\Desktop\ARD_v1\ARD_ESP-IDF\ImageSenderMCU\build.ps1" build
& "C:\Users\work\Desktop\ARD_v1\ARD_ESP-IDF\JC1060P470C\build.ps1" build
```

적용 후 PC 시작→완료→JC1060 시작을 반복하고, 촬영 실패 시 자동 1회 재시도/최종 복구와 수동 초기화 후 재시작을 확인한다. 증상이 남으면 ImageSender의 `ping` 결과와 `Capture accepted`, `Frame timeout`, 업로드 실패 로그 및 PC 선별 오류 문구가 다음 진단 자료다.
