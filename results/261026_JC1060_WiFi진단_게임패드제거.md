# JC1060 Wi-Fi DHCP 진단 및 게임패드 제거 (2026-10-26)

## 실물에서 확인한 증상

COM22, 115200 baud로 로그를 수집했다. 개방형 `UCW-E2-208-2`와 모바일
핫스팟 `A35_m` 모두 무선 연결은 성공했지만 IP 할당 이벤트가 없었다.
연결 요청부터 25초가 지나면 `ESP_ERR_TIMEOUT`으로 종료했다. 무선 연결에
약 5초가 걸려 실제 DHCP 대기는 약 20초였다.

설정 복구 중 나오는 `YOUR_WIFI_SSID`는 NVS에 저장된 이전 값이다.
이 프로필의 `reason 201`을 시험 대상 네트워크의 인증 실패로 해석하면 안 된다.

실제 P4는 리비전 1.3, 부트로더와 앱의 ESP-IDF는 5.5.5였다.
부팅 로그에서 C6와 호스트의 ESP-Hosted가 모두 2.12.2이고, 양쪽 SDIO가
streaming 모드를 사용함을 확인했다. 단순한 버전 불일치로 단정하지 않았다.

## 변경 내용

- 수동 연결의 무선 연결 대기 25초와, 무선 연결 후 DHCP 대기 30초를 분리했다.
  반복 연결에도 전체 작업은 최대 90초로 제한한다.
- `ARD_WIFI_DIAGNOSTICS` 옵션과 `WIFI_DEBUG` 로그를 추가했다. STA의 DHCP
  상태, IP/게이트웨이/넷마스크, MAC, TX/RX/ARP 패킷 수와 오류를 기록한다.
- DHCP 메시지 종류와 transaction ID를 기록한다. 패킷 내용과 비밀번호는
  출력하지 않는다. SDK 수신 오류 보고도 진단 옵션과 함께 켠다.
- 공개 netif 경계에서 기존 콜백과 핸들을 보존해 송수신을 관찰한다.
  수신 버퍼를 전달하기 전에 필요한 헤더 정보만 복사하며 버퍼 수명은 바꾸지 않는다.
- JC1060의 게임패드/HID 파서/입력 작업 소스와 페어링·상태 UI를 삭제했다.
  게임패드 PTT와 축 입력 전송도 제거하고 P4의 Bluetooth를 비활성화했다.
- 터치 화면의 모터 명령과 E-STOP/RE-ARM 독립 전송 경로는 유지했다.
  PC 화면의 게임패드 안내 문구도 제거했다.

## 빌드 및 실물 시험 기록

기존의 불완전한 `managed_components`는 작업 폴더의 `tmp`에 보관한 뒤
`dependencies.lock`의 고정 버전으로 복원했다. 기존 `build`를 지우지 않고
`build/wifi_debug`를 사용했다. 로컬 환경 설정은 `tmp/build_jc1060_debug.ps1`에 있다.
SDK 활성화에 필요한 `ESP_IDF_VERSION=5.5`도 적용해 C6 선택을 확인했다.

게임패드 제거 전의 진단 펌웨어는 ESP-IDF 5.5.5로 컴파일·링크·이미지 생성에
성공했다. 이 이미지는 장치에 올리지 않았다. 게임패드 제거 후 최종 빌드와
업로드·IP 할당 결과는 아래에 추가한다.

시험 전 장치의 0x8000부터 0x608000바이트를 `tmp`에 백업했다.
기존 파티션은 NVS 0x9000/0x6000, PHY 0xf000/0x1000, 앱 0x10000/0x600000이다.
시험 업로드는 앱 영역만 대상으로 하며 NVS를 지우지 않는다.

### 게임패드 제거 후 1차 빌드 및 업로드

- ESP-IDF 5.5.5 컴파일·링크·이미지 생성·파티션 크기 검사: 종료 0.
- 앱 크기: 3,150,352바이트(`0x301210`), 6 MB 앱 파티션 내 수용.
- 앱 SHA-256: `64d9095c944892af911a1585be1afcd9766ad0b51a10e7a206168ff280b15753`.
- 생성된 설정에서 Bluetooth 비활성화를 확인했다. 최종 링크 맵에
  `gamepad_start`, `nimble_port_run`, `ble_gap_disc`, HID 게임패드 파서가 없다.
- 진단용 두 netif wrapper가 실제 링크됐음을 확인했다.
- COM22에서 앱 영역 `0x10000`만 업로드했다. 종료 0, 장치 해시 검증 성공.
- 재부팅 후 새 앱(`715f720-dirty`, ELF SHA 시작 `efeeaa942`)을 확인했다.
  `Host BT Support: Disabled`, `DHCP trace enabled`,
  `STA data-path trace installed=1`이 출력됐다.
- 사용자의 재시도에서 실제 선택된 네트워크는 `UCW-E2-208-2`였다.
  DISCOVER/OFFER/REQUEST/ACK가 같은 transaction ID로 이어졌고
  `100.105.4.107`을 받았다. 설정 저장과 약 70초 연결 유지도 확인했다.

### 재부팅 시험에서 발견한 MAC 초기화 문제와 보강

1차 펌웨어 재부팅 시험에서는 STA 인터페이스의 MAC이 모두 0인 상태로
DHCP DISCOVER를 반복했고, 자신의 transaction ID에 대한 OFFER가 없었다.
다른 클라이언트의 DHCP 패킷은 수신돼 전체 C6→P4 수신 단절과 구분할 수 있었다.
설치된 lwIP 코드가 인터페이스의 `hwaddr`를 DHCP `chaddr`로 복사하는 것도 확인했다.

`wifi_station_mac.c`에서 실제 C6 STA MAC을 읽어 검증하고, DHCP가 시작되기 전
인터페이스의 MAC을 맞추도록 했다. 기존 앱 연결 이벤트 처리기가 IDF 기본
처리기보다 먼저 등록되는 순서를 유지했다. 아직 내려간 인터페이스만 보정하며
무선 장치의 MAC은 바꾸지 않는다. 적용 후 읽기 검증과 오류 기록도 수행한다.

`test/run_wifi_station_mac.py`는 실제 보정 C 코드를 실행하며 14개 경우를
검사했다. 0 주소 보정, 이미 일치한 주소, 유효하지 않은 무선 주소, 동작 중인
인터페이스 보호, SDK 오류와 읽기 검증 실패를 포함하며 종료 0이었다.

- 두 번 모두 무선 MAC과 호스트 MAC이 `10:bd:a3:9a:50:60`으로 일치했고,
  자신의 transaction ID로 OFFER/ACK를 수신했다. 관찰 구간 TX/RX 오류는 0이었다.
- `Host BT Support: Disabled`를 확인했고 게임패드/NimBLE 검색 로그가 없다.
  Wi-Fi 진단은 계속 활성화돼 있다.

핫스팟 재시험과 전원 완전 차단·재인가 시험은 이번 기록에 포함하지 않는다.
